# 文件夹传送 v2：会话卡片、海量文件、可靠续传

> 设计修订稿，尚未实现。参考 `migrate-yaxin-to-m5.sh` 的 preview / sync / verify、
> progress2、partial-dir、日志和两端防休眠体验；不照搬 SSH、Homebrew 安装流程。
> 产品原则：用户理解的是“向某台电脑发送文件夹”，不是“发布 token 后调用下载接口”。

## 1. 对原方案的评估与纠正

对话卡片、后台续传、只读源目录的方向合理，但原方案不能直接落地：

| 原方案的问题 | 修订 |
|---|---|
| 整棵目录一次返回 JSON，上限 10,000 项 | 无人为文件总数量上限；持久化索引、可恢复分页、有限内存队列 |
| “同步整个文件夹”含义模糊 | 默认叫“接收文件夹”，是一次性复制，不是持续同步、镜像或双向同步 |
| 点击目录按钮就发布长期共享 | 默认一次性传送；“允许对方按需浏览”才是显式高级选项 |
| 实时日志、发送方进度放到 P1 | 两端任务进度、速度、百分比、持久化日志列为基础交付要求 |
| 全部文件、完成集合保存到大 JSON，逐文件重写 | SQLite 分表记录任务、条目、断点；事务批量提交，不全量重写 |
| `size + version` 就认为目标文件可跳过 | 远端版本不是本地内容的证明；使用历史校验记录与本地检查，必要时重算哈希 |
| 原下载函数完全复用 | 仅复用分块/校验逻辑，拆出任务调度、进度、取消和消息呈现；不能每个文件发一条聊天消息 |
| 单并发逐文件下载 | 先有界并发（初始 2，最多 4），再通过实测调优；避免无限请求或单个小文件往返拖慢全局 |
| 未区分权限错误、离线、源变化 | 明确错误分类及对应动作，不一概重试三次 |
| 完成后跟当前源目录校验 | 默认对本次任务清单校验；与最新源目录比较是另一项操作，不能混为一谈 |

脚本语义也需准确理解：`-aHX` 是归档及硬链接、扩展属性保留，不代表“已存在就跳过”。
rsync 常规快检基于大小和修改时间，`--checksum` 才做内容比较；该脚本可能更新同名目标文件，
不删除目标多出的文件，也不是实时同步服务。新方案默认更保守：不覆盖、不删除。

## 2. 交互目标：一个传送任务，一张会话卡片

### 2.1 发起方式统一

- 点击输入栏“文件夹”按钮或从 Finder 拖入文件夹，默认都表示“发送这个文件夹”。
- 发送文件/多选文件也进入同一任务模型，大文件无需用户寻找“断点续传模式”。
- 文件夹默认包含隐藏文件（开发项目需要 `.git` 等）；准备区明确提示，可展开排除规则。
  一次性传送与高级只读浏览使用相同规则，并在清单中记录，不能一边跳过隐藏文件一边全部公开。
- 不让用户处理 `antify-share://` 地址；复制地址仅在高级共享的“更多”菜单内提供。
- 无需输入自然语言命令：“对话式”指所有操作都在设备会话上下文中完成。

拖入时沿用当前交互：只有右侧主区出现蒙版，中央提示“松开发送到「主机名」”；左侧列表不变。
拖入并松手后进入该会话的准备卡，固定目标设备，后续切换会话不能改变任务接收方。

### 2.2 桌面拖入与浏览器降级

当前桌面壳禁用了 Tauri 原生文件拖放，页面通过 HTML5 File/Entry 流中转。
这条路径不能保证应用重启后重新打开原文件，不应宣称等价于原生路径任务的持久续传。

- 桌面版需重新设计受控原生拖放桥接：原生层接收用户拖入的路径并登记为任务源，
  UI 只持有不可伪造的源句柄，不允许远程页面传任意路径读取本机文件。
- 与右侧拖放蒙版/当前会话命中逻辑一并整合，不能简单开启原生拦截而丢失 HTML 拖放反馈。
- 文件选择器与原生拖入共用源登记；路径权限仅覆盖用户这次选择的根目录。
- 普通浏览器保留中转模式，但明确标注重启恢复可能需要重新选择源目录并验证内容身份。
  超大目录建议使用桌面端，不通过把整目录先上传到内存来伪装原生支持。

### 2.3 发送前的轻量准备卡

```
📁 yepeng
正在整理目录… 已发现 12,480 个文件 · 86.2 GB
发给：M5    包含隐藏文件
[发送]  [选项 ▾]  [取消]
```

- 立即显示卡片，不等待全量扫描或全文件哈希后才反馈。
- “发送”可在扫描中点击：发送任务邀请，扫描在后台继续；大小标注“统计中”。
- 选项默认折叠：排除规则、一次性传送 / 允许按需浏览。目录选择器选完也复用此准备卡。
- 尚未发送时只创建本地准备任务；取消会停止扫描，不开放远程访问。
- 接收方未接受前可以扫描元数据，但不主动读取全部文件内容做昂贵哈希。

### 2.4 接收卡片

```
📁 yepeng                      来自 M1-Air
12,480 个文件 · 86.2 GB（仍在统计）
保存到：下载/yepeng                  [更改]
[接收文件夹]  [查看内容]  [拒绝]
```

- 默认新建友好的顶层文件夹，不暴露 `Shared-<token>` 作为用户看到的名称。
- 有重名时默认保留双方；“比较并更新已有目录”是显式高级操作，不默认覆盖。
- “查看内容”在卡片内展开有限高度列表：面包屑导航、懒加载、虚拟列表；不把大文件树铺满会话。
- 不可信设备必须明确接受；可信设备自动接收是独立用户设置，不能因收到地址自动下载。
- “我的共享”移至会话更多菜单，仅管理长期共享；普通用户无需打开独立共享对话框。

### 2.5 传输中：卡片原地更新，不刷消息、不抢滚动

```
📁 yepeng                       接收中
██████████░░░░░░░░░░   63.4%
54.5 / 86.0 GB · 82.3 MB/s · 约剩 6 分钟
8,920 / 12,480 个文件已完成
当前：projects/video.mov
[暂停]  [详情 / 日志]  [更多 ▾]
```

- 发送方同样可见发送速度、对方确认进度；确认失联时显示“等待对方确认”，不能伪报完成。
- 主操作随状态切换为暂停/继续/重试；“取消任务”放入更多菜单，减少误触。
- 暂停保留已完成文件及断点；取消需确认，默认不删除已完成文件，清理临时文件单独选择。
- 详情折叠显示当前文件进度、校验阶段、跳过/冲突/失败数；日志默认收起。
- 会话切换、窗口关闭、页面重载不停止后台任务；返回会话恢复同一张卡片。
- 进度更新只更新卡片局部节点，不重绘整个会话、不自动跳到底部。
- 多任务用紧凑排队卡；左侧不增加拖拽高亮，也不随每次进度跳动重排。

### 2.6 结果卡

```
✅ yepeng 已接收
12,480 个文件 · 86.0 GB · 用时 18 分钟
内容校验通过 · 跳过 23 项 · 保留重名 2 项
[打开文件夹]  [查看日志]  [更多 ▾]
```

- 有失败项显示“部分完成：3 个文件未传送”，主按钮“重试失败项”，不能显示绿色全部成功。
- 全文件内容校验并落盘发布后才算完成；“数据收完，正在校验”不等于完成。
- 更多菜单：重新校验本次副本、导出报告、再次传送；长期共享可撤销访问。
- 逐个文件不单独追加消息；接收结果清单在卡片详情分页查看。

## 3. 无人为文件数量上限的目录处理

### 3.1 “无上限”的边界

不设置 1,000 / 10,000 / 100,000 个文件之类的产品总量门槛，也不要求用户拆文件夹。
实际受磁盘空间、文件系统、可用资源限制；达到资源限制时明确暂停并提示，不截断清单。
每页大小、单响应体积、并发数、扫描队列内存仍需上限，这是资源保护而非文件总数限制。

### 3.2 持久化扫描 + 稳定分页

- 共享方创建 `manifest_id`，用工作线程增量扫描，将目录和文件条目写入 SQLite。
- 待扫描目录也是持久化工作队列；处理单个超大目录时逐条枚举，不能 collect 全目录到内存再排序。
- 每个条目有递增 `entry_id`、相对路径、类型、大小、修改时间、源版本信息。
- 接收方用 `manifest_id + cursor` 分页拉取，例如每页最多 500 项并同时限制响应字节数。
- 游标对应数据库稳定条目序号，不用实时文件系统列表的 offset，避免增删导致跨页重复或漏项。
- 返回 `next_cursor / scan_state / known_files / known_bytes`；正在扫描但暂时没新条目不等于扫描结束。
- 接收方每页事务写入条目表并保存游标；请求重放通过唯一键去重，断线可继续。
- 文件内容不写入 manifest JSON；哈希按待传文件计算及缓存，不为统计总大小预读整个目录。
- 前端仅拉聚合进度、可见目录页、日志增量；不能把整个任务清单加载到浏览器。

### 3.3 扫描与百分比的诚实性

默认“完整扫描 → 计划固定 → 传输”：扫描时实时显示已发现数量/大小和扫描耗时，不伪造百分比；
完整计划确定后显示准确的传输总百分比，分母不再随文件发现增长。

可后续增加“边扫描边传”模式降低超大目录首文件等待：扫描结束前显示“已传 X GB，总量统计中”，
不显示貌似准确的总百分比；扫描完成后切换为固定分母。无法同时承诺未知总量与准确总百分比。

### 3.4 源目录不是静态快照

分页清单稳定不等于文件系统内容被快照：扫描和传输期间源文件仍可能变化。
每文件读取前后检查版本，接收块和最终文件校验；发现变化标为“源文件已变化”，不混合新旧内容。
受影响条目允许重新扫描/重试，创建新的计划修订并在 UI 明示总量变化，不偷偷把进度倒退。
对持续写入的项目提示关闭相关程序或使用用户提供的文件系统快照后重传；不保证热目录的时间点一致性。

## 4. 实时速度、进度与时间的定义

### 4.1 指标分开记录

- `planned_bytes`：本次固定计划中需要接收的逻辑字节（排除已确认无需复制的文件）。
- `verified_bytes`：上述计划中已校验并持久化的有效字节，包含恢复的有效断点，重试不得重复累计。
- `network_bytes`：本次运行实际接收的应用层数据字节，包括失败重传；不等于网卡物理吞吐量。
- `completed_files / planned_files`：文件及其最终校验完成数；目录/空文件另有状态记录。
- `skipped_bytes / reused_bytes / failed_files`：独立展示，不混成“本次网络发送量”。

任务内每个工作线程报告增量，聚合器生成单调序号事件，按 task_id 更新 UI。

### 4.2 刷新与计算

- 服务端从网络流读取时更新流量计数，不等整个 4 MiB 块写完才更新网速。
- UI 每 500ms～1s 接收一次节流更新；SSE 为主，断线后补快照/重连，轮询为降级。
- 速度使用最近 3～5 秒实际传输字节的滑动平均，暂停和失联后显示 0 / “已暂停”，不保留旧速度。
- 固定计划的传输百分比 = `verified_bytes / planned_bytes × 100%`；恢复后不从零开始。
- 当前块可显示临时接收进度，但未校验部分不能记成可恢复断点。
- ETA 用剩余有效字节 / 有效完成速度估计，样本不足、扫描、暂停、等待上线时显示“估算中”或“—”。
- 全部数据收齐但最终校验未完，显示“数据 100%，正在校验”；完成状态需独立判定，不能只判断百分比。
- 仅有空文件/空目录或全部跳过时按条目完成情况处理，避免除零。
- 速率单位明确为 MB/s；详情可展示 Mbps。平均速度区分活跃传输耗时与含暂停的总耗时。

发送方展示自身实际发送速度；接收方的落盘/校验百分比通过任务状态回执返回，双方数值不必瞬时完全相等。
回执可重试且幂等；仅收到最后一块请求不能被当作接收完成。

## 5. 连续传输与恢复引擎

### 5.1 数据模型

建议 SQLite 表：
- `transfer_tasks`：task_id、offer_id、会话/消息 ID、peer 指纹、manifest_id、固定目标路径、
  选择范围、排除/冲突策略、状态、计划修订、聚合计数、时间和恢复意图。
- `transfer_entries`：task_id、entry_id、相对路径、源版本/哈希、大小、目标实际路径、状态、错误、重试次数。
- `transfer_checkpoints`：文件身份、块边界、已校验偏移/必要的块校验记录。
- `scan_jobs / manifest_entries`：共享方扫描队列、分页清单和版本记录。

索引支持按状态/任务分页；任务行不保存无限增长的数组。写入采用有界批次事务。
同一邀请重复点击接受返回同一任务；同一文件最多一个 worker 写入；目标冲突名落盘后保持稳定。

### 5.2 拆分现有下载函数

现有 `shares.rs::download()` 混合全局 PullState、命名、IO、整文件校验和 `push_chat`，不能原封不动当批量引擎：
- 拆为无 UI 副作用的 `transfer_entry(task_context, entry, progress_sink, cancellation)`。
- 全局 cancelled/progress 改为按任务隔离；旧单文件下载也进入统一调度，避免两套引擎竞争。
- 每文件传输结果只更新任务条目，不发一条聊天消息。
- 现有暂存 key 实际包含 peer、token、path、SHA-256、size；新实现还要区分目标任务/目录，防并发写同一 part。
- 不能仅凭 `.part` 长度断言其内容已校验；显式落盘断点，遵循先数据持久化、后提交检查点。
  崩溃后核对/复验必要块，最终整文件哈希始终必做。
- 文件发布成功与任务完成记录之间若崩溃，下次需对账已发布目标，不能再次另存一个副本。

### 5.3 调度与性能

- 有界并发，初始 2 个文件 worker，全局最多 4 个，并支持每设备限额；通过小文件/大文件/机械盘实测调优。
- 同一大文件先顺序分块、有界缓冲；不能把数十 GB 文件读入内存。
- 复用 HTTPS client/连接池；哈希与阻塞文件 IO 放受限工作线程，不阻塞 async runtime。
- 缓存与源版本绑定的哈希；不反复对未变化大文件全量读取。
- 避免每个小块强制刷盘导致速度崩溃：设置有界刷盘批次，但只宣称持久化部分可续传。
- 先保证正确性，再优化大量小文件的往返开销；后续可加有界小文件批传，不能用整目录压包换取不可恢复的大任务。

### 5.4 重试、恢复、冲突

- 网络瞬断：指数退避加抖动，有限自动重试；掉线转等待状态，以设备指纹重新发现地址，不能固定旧 IP。
- 权限拒绝/共享撤销/源文件不存在：明确分类，不无限重试；撤销不得自动重新授权。
- 磁盘不足：整任务暂停，检查实际下载卷/暂存卷空间，提示更换路径或清理；传前预检不能代替传中检测。
- 单文件坏块/不可读：有界重试后继续其他条目，结果标为部分完成。
- 用户暂停不因设备上线自动恢复；应用意外退出后默认“待继续”，可显式设置自动恢复。
- 同任务恢复跳过已完成文件前核对本地状态；远端 size/version 相同不能证明本地内容没变。
  对未知的同名文件做内容比较或保留双方，不能直接跳过。
- 默认新目录保留双方；高级“比较并更新”需预览和确认，明确可能替换同名文件但不删除额外文件。

### 5.5 文件语义与安全

- 保留目录结构和空目录；明确处理隐藏文件、权限不可读项、超长路径及 Windows 大小写/保留名冲突。
- 默认不跟随符号链接，报告跳过原因；所有路径在共享根/下载根内校验，拒绝越界和链接替换攻击。
- 内容复制第一阶段不声称等价于 rsync `-aHX`：硬链接关系、权限、扩展属性、macOS resource fork 等需单独能力声明。
  可保留支持范围内的修改时间；属性丢失必须有报告，不能标为完整系统迁移成功。
- 两端活跃 IO 期间持有平台电源断言，引用计数管理；暂停/终止释放。
  防空闲休眠不承诺阻止合盖/用户强制睡眠，断开后仍走续传。

## 6. 日志是基础能力，不是附加功能

### 6.1 实时可见

卡片“详情 / 日志”展开后：

```
14:20:01  开始整理 yepeng
14:20:12  清单完成：12,480 文件，86.0 GB
14:20:13  接收开始，保存到 下载/yepeng
14:21:07  完成 projects/a.zip，2.1 GB，SHA-256 通过
14:21:08  同名文件已保留双方：notes (1).txt
14:23:10  网络中断，等待 M1-Air 上线；断点已保存
14:23:42  恢复传输，从 18.4 GB 继续
```

- 后台追加持久化 JSONL（机器可读），UI 提供文本视图及导出文本/JSONL。
- 每条记录含 event_id、时间、task_id、阶段、相对路径、结果、字节数、错误分类、重试信息。
- 网速/进度是高频内存事件，按较低频率记录汇总（例如 10 秒一次）；不为每块刷一行日志。
- 完成/失败/重试/暂停/恢复/冲突/校验/撤销等关键事件及时持久化。
- UI 只保留最近一页（例如 200 条），按游标加载历史，支持全部/异常筛选、复制、导出。
- 暂停自动滚动：用户翻看历史时不被新日志拉走；页面关闭后后台日志继续记录。

### 6.2 保存与容量管理

- 日志放应用数据目录 `logs/transfers/<task_id>/`，路径可通过“打开日志目录”访问。
- 分卷轮转，历史卷可压缩；运行任务不静默删除历史。空间不足暂停并提示，不能假装日志完整。
- 已完成任务的保留周期可设置（例如 30 天），导出后由用户管理；结果摘要单独保留。
- 日志不含共享 token、完整凭证 URL、文件内容；导出提示路径/主机名可能包含隐私。
- 日志不是恢复数据库，恢复以 SQLite/检查点为准；双写崩溃通过 event_id 对账，避免依赖文本解析恢复任务。

## 7. 协议、安全与兼容

- 默认“发送文件夹”是有接收确认、限定接收设备身份及有效期的一次性邀请。
- 现有共享是持有 token 即可访问；仅在 UI 写上 peer 指纹不构成访问限制。
  新协议需有可验证的 peer 身份认证/握手，并将短期访问授权绑定到该身份、邀请和范围。
  这属于必须实现并测试的安全工作，不能假定现有服务端已支持。
- 持久化凭证需最小权限保存，不放进日志；授权续期或对端身份变化需明确处理。
- 一次性邀请完成后终止内容访问，保留结果回执通道及重连确认宽限期；
  未完成任务按配置的有效期保留恢复授权，过期后会话卡提示重新授权。
- 长期只读浏览单独显式确认；兼容旧 bearer 地址时说明“持有地址的人可读取”，不能声称绑定收件人。
- 新版先协商能力，结构化任务消息带版本及 offer_id，元数据有长度限制并当不可信输入处理。
  清单、目标大小和路径均由受验证接口获得，不信任聊天文字里的统计。
- 旧 AntifyBot 保留原地址浏览方式；官方 LocalSend 提供明确的普通发送降级选项。
  兼容通道自身数量/续传限制要提前说明，不能对所有客户端宣称海量文件可靠续传。

建议新增独立版本化传输 API，而不是往单文件 manifest 接口塞递归全量 JSON：
- 邀请/接受/拒绝/能力协商。
- manifest 创建、扫描状态、条目 cursor 分页。
- 文件版本/哈希、范围读取（复用并完善现有协议）。
- 任务进度回执及完成确认（有序、幂等、可重试）。
- 本机任务创建、分页查询、暂停/恢复/取消/重试/校验。
- 本机 SSE 任务事件、日志游标读取和导出。

## 8. 实施顺序与验收

不建议把原方案直接“一次改完发版”，先完成以下依赖链：

1. 引擎与数据：任务隔离、SQLite 清单/检查点、稳定分页、崩溃对账、IO 与 UI 解耦。
2. 可靠性与观察：有界调度、续传、速度统计、日志、磁盘检测、源变化处理、防休眠。
3. 会话整合：准备/接收/进度/结果卡、两端回执、兼容协商与授权；旧消息仍可查看。
4. 大规模验证后发布：以上都是本次可用版本的交付条件，不能把无限数量、实时指标、日志推迟到后续版本。

优先做完整文件夹接收；多层任意勾选、边扫描边传、高级更新目录、限速和元数据完整迁移可后续增加。

验收至少覆盖：
- 超过 10,000 / 100,000 项及百万级混合目录压力测试：不触发数量门槛，内存/响应体有界，目录单层巨大也可处理。
- 数十/数百 GB 单文件：网速持续刷新、总百分比正确，重试不重复累计，最终校验完整。
- 空目录/空文件、隐藏文件、长路径、大小写冲突、源文件变更和撤销权限。
- 断网、IP 改变、暂停、进程强杀、发布成功但完成记录未提交：恢复不混版本、不重复另存、不误报成功。
- 磁盘耗尽、日志卷满、数据库写失败：受控暂停并给出可执行的提示。
- 页面/窗口关闭后继续传输，重新打开恢复原任务卡；单个百万文件任务不生成百万条消息。
- 两端进度回执丢失或乱序：发送方等待确认，重连收敛，不能根据发完字节就宣称对方完成。
- 对照脚本核验文件内容；属性保留差异单独列出；未实现项不标为 rsync 等价。

性能数字需在实际 Wi-Fi/有线网络、SSD/机械盘、大文件/小文件混合场景测量后给出，
不预先承诺某个 MB/s 或“和 rsync 一样快”。
